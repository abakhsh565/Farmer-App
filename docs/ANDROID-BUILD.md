# Building the Android APK locally

The farmer app is packaged as a native Android application with Capacitor, so the
installable APK runs the same code as the web build rather than a re-implementation
of it. The reasoning is in [PRD-ALIGNMENT.md](./PRD-ALIGNMENT.md); the practical
consequence is that there is one UI to maintain, and it is the approved one.

## One command

```bash
npm install          # first time only
npm run apk
```

That runs, in order:

1. `npm run build` — typecheck, then Vite builds the web app into `dist/`
2. `cap sync android` — copies `dist/` into the Android project's assets
3. `node scripts/build-apk.mjs` — selects a JDK, resolves the Android SDK, runs
   Gradle `assembleDebug`, and copies the result out

Output:

```
artifacts/farmer-app-debug.apk
```

## Installing on a phone

Enable USB debugging on the device, connect it, then:

```bash
adb install -r artifacts/farmer-app-debug.apk
```

`adb` lives in the Android SDK at `platform-tools/adb`. If `adb` is not on your
`PATH`, use its full path, for example:

```bash
"C:/Users/<you>/AppData/Local/Android/Sdk/platform-tools/adb" install -r artifacts/farmer-app-debug.apk
```

Alternatively, copy `artifacts/farmer-app-debug.apk` to the phone and open it;
Android will ask you to allow installation from that source.

## Requirements

| Requirement | Notes |
| --- | --- |
| Node 20+ | to build the web app |
| Android SDK | with `platforms/` and `build-tools/`. Found via `ANDROID_HOME` or the default per-user location |
| **JDK 17–23** | see below — this is the part that catches people |
| Internet on first build | Gradle downloads its distribution and dependencies |

## The JDK trap, and why the script exists

Gradle 8.14's Groovy compiler **cannot run on Java 24 or newer**. Android Studio
on this machine bundles Java 25, so building with the obvious JDK fails with:

```
BUG! exception in phase 'semantic analysis' in source unit '_BuildScript_'
Unsupported class file major version 69
```

68 is Java 24; 69 is Java 25. That message does not mention Java, so it is easy
to misread as a Gradle or Android plugin problem.

`scripts/build-apk.mjs` therefore searches for a JDK whose major version is
between 17 and 23 and picks it, in this order:

1. `JAVA_HOME`, if it is already a supported version
2. `~/.jdks/*` — the per-user JDKs Android Studio and IntelliJ manage
3. System install locations for common vendors, and Android Studio's bundled
   runtime (listed so it can be rejected with an explanation rather than used)

On this machine the working one is `~/.jdks/jbr-21.0.11`, which is why
`JAVA_HOME` does **not** need to be set by hand.

If no suitable JDK exists, the script stops and says so instead of failing
obscurely inside Gradle. Install Eclipse Temurin 21 and re-run.

### The second trap: `local.properties`

A Windows path written with backslashes is read by Java's `Properties` loader as
escape sequences, and Gradle reports the result as:

```
java.io.IOException: Invalid file path
```

The script writes `sdk.dir` with **forward slashes** for exactly this reason. If
you write `android/local.properties` yourself, do the same.

## Manual build (if you would rather not use the script)

```bash
# 1. a JDK Gradle accepts
export JAVA_HOME="$HOME/.jdks/jbr-21.0.11"

# 2. point at the SDK, forward slashes
printf 'sdk.dir=C:/Users/<you>/AppData/Local/Android/Sdk\n' > android/local.properties

# 3. build the web app and sync it into the Android project
npm run build
npx cap sync android

# 4. build the APK
cd android && ./gradlew assembleDebug

# result
android/app/build/outputs/apk/debug/app-debug.apk
```

## Release builds

`assembleDebug` produces a debug-signed APK that is installable but not
publishable. A release build additionally needs a signing key:

```bash
keytool -genkey -v -keystore release.keystore -alias farmer \
  -keyalg RSA -keysize 2048 -validity 10000
```

then `android/app/build.gradle` needs a `signingConfigs.release` block reading
those values from environment variables or `~/.gradle/gradle.properties` — do not
commit the keystore or its password. This is deliberately **not** wired up yet:
the signing identity is a business decision, and a keystore generated by an agent
would be the wrong one to ship.

## Important: the current APK runs in local mode

The APK built today contains the complete UI and all on-device behaviour, but it
has **no backend credentials compiled in**, so it runs against the local
development providers and keeps every document on the device.
That is why it is a debug artifact for hands-on testing, not a release candidate.

Once the Supabase values in [CREDENTIALS-REQUIRED.md](./CREDENTIALS-REQUIRED.md)
are in `.env.local`, re-run `npm run apk`; the same command then produces an
APK wired to the real backend. `VITE_*` variables are inlined at build time, so a
rebuild is required — restarting the app is not enough.
