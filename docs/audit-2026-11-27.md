# Farmer App — audit and build blueprint (2026-11-27)

Scope: the whole `src/`, `api/` and `supabase/functions/` tree on branch `development`.
Evidence: import graph over 277 source files, line counts, dependency scan, the 954 KB
production bundle, the running dev app at `127.0.0.1:5173`, and `npm run check:fast`
(typecheck + lint + 658 tests, 110 s).

The single most useful number here: **only 1,214 of 56,638 lines were dead**. The app is not

screens, a dev/remote provider pair, and a deep provider stack — not in leftover files. That
changes the plan: deleting cannot make this app small. Only deciding what the app *is* can.

## 3. Where the weight actually is

| Hotspot | Size | Verdict |
|---|---|---|
| `src/i18n/catalog.ts` | 3,090 lines | Data, not logic. Keep. |
| `src/screens/ReviewScreen.tsx` | 1,452 lines | A whole product inside one screen (crop review). Candidate to split or cut. |
| `src/screens/AssistantScreen.tsx` | 1,069 lines | Chat + tools + voice in one file. |
| `src/shop/ShopApiProvider.tsx` | 939 lines, 18 callbacks | Cohesive but overloaded: credentials, shops cache, threads, media outbox, polling, alerts, deep links. |
| `src/session/CredentialSheet.tsx` | 928 lines | Code entry + QR + invitation + copy — the "optional 10%" path costs a full screen. |
| `src/services/persistence.ts` | 902 lines | One storage layer; fine. |
| `src/services/providers/develop.ts` | 874 lines | Dev-only fixtures. Keep out of production bundles (already done). |
| `src/services/providers/remote.ts` | 738 lines | The real backend. |
| `src/App.tsx` | 469 lines, 13 providers | Every feature's state lives in the tree root. |

Two structural costs show up over and over:

1. **Provider depth.** 13 nested providers mean every new feature has to be threaded through
   `App.tsx`, and every screen re-renders when any of them changes. Four of them
   (`Visit`, `Insight`, `Credit`, `AiCredits`) are thin wrappers over a store that already
   exists in `src/*/store.ts` — they can be read directly with `useSyncExternalStore`.
2. **Two of everything in `services/`.** `develop.ts` and `remote.ts` implement the same
   interface, so any new endpoint is written twice. That is the price of a fake backend,
   and it is paid on every feature.

## 4. The blueprint — the smallest shape that does this job

The product is: *a farmer sees the shops within 100 km and talks to them.* Everything else
is secondary. Build it in this shape and stop there:

**Four screens, one job each**
1. `Home` — weather, today's action, one line per connected shop.
2. `Shop` — list by distance + search + product filter → shop detail → conversation.
3. `Chat` — the conversations that already exist, opened from Shop.
4. `Profile` — phone, location, connection, language.

**One state layer per domain, no more than six providers**
`Theme/Locale` → `Services` (environment + clients) → `Session` → `Location` → `Shop` → `Chat`.
Delete the wrapper providers over existing stores; screens subscribe to the store.

**One client per backend, one cache rule**
- App backend: `supabaseClient.ts`.
- Dealer backend: `shop/api/client.ts`.
- Cache: memory + `localStorage`, paint cache first, refresh in the background
  (`ShopApiProvider` already does this for shops — make it the rule everywhere).
- Polling only while a conversation is open. Never on list screens.

**The exact build order for any new feature**
1. Endpoint in `services/types.ts` + `remote.ts` (and `develop.ts` only if a screen needs it offline).
2. Cache key + stale-while-revalidate read.
3. Screen renders from cache, then the fresh value.
4. Test the empty, loading, error and offline states — that is the whole test budget.

**What not to add** (each one is a permanent cost, and none is required by the product):
a second code-entry surface, a second way to fetch shops, per-feature providers,
animation libraries, an ORM, a state library, realtime infrastructure for a 1:1 chat that
five seconds of polling already covers.

## 5. Quick wins, in order

1. **Shop empty state has no action.** Observed on the dev build: guest mode shows
   "0 DEALERS WITHIN 100 KM … Increase the radius or search another area", but there is no
   radius control and no sign-in/connect button on that screen. A farmer who is not linked
   sees a dead end. Add one button: "Connect a shop" (or "Sign in") in that empty state.
   Effort S.
2. **Fold four wrapper providers into their stores.** Removes four levels from `App.tsx`.
   Effort M, no behaviour change.
3. **Split `ReviewScreen` and `AssistantScreen`.** They are the two files most likely to
   make every future change slow. Effort M each.
4. **Move the 10% code path out of `CredentialSheet`.** The screen is 928 lines for a path
   most farmers never use; a sheet with "paste code / scan QR" is enough. Effort M.

## 6. What was not done, and why

- No feature was deleted. Removing `ReviewScreen`, the community or the credit ledger is a
  product decision, not a cleanup: they are wired, tested and shipping.
- No refactor of `ShopApiProvider`, `App.tsx` or the provider stack was attempted in this
  pass. Both are behaviour-bearing and need their own change with tests, not a drive-by.
- The audit is import-graph and measurement based; it did not read all 56k lines, so
  internal duplication inside large files is not quantified beyond the notes above.
